一、需求追溯链路

需求不是拍脑袋列出来的，每一条都能往回追到痛点。

用户痛点（Day 2 第五章）
    ↓
用户故事（Day 2 第四章，US-1 ~ US-14）
    ↓
需求启示（Day 2 第六章，R1 ~ R12）
    ↓
功能需求（本文档，F1.1 ~ F6.6）

示例：客服"在 4 个平台后台间切换"（痛点）→ US-1"希望消息汇总到一个工作台" → R1"全渠道会话聚合" → F1.1 多渠道会话接入。

这条链路的价值在于：任何一条需求被挑战时，都能说清它为什么存在。

二、优先级方法

采用 MoSCoW 法，每条需求从三个维度打分后定级。

等级 定义 判定标准
Must 必须有。缺了产品不成立或核心价值链断裂 不满足则无法交付核心价值主张
Should 应该有。重要但不致命，可延后一个版本 影响体验或效率，但不阻断主流程
Could 可以有。锦上添花，资源充裕时做 有更好，没有也不影响决策
Won't 本期不做。明确排除，避免范围蔓延 与定位不符、ROI 过低或依赖未成熟

打分三维度

维度 说明
用户价值 覆盖多少用户？解决多痛的痛点？（参考 Day 2 痛点严重度）
实现成本 研发工作量、技术难度、外部依赖复杂度
依赖关系 是否为其他需求的前置条件

本期统计：Must 16 条 / Should 12 条 / Could 5 条 / Won't 6 项

三、功能需求清单

F1 会话工作台

编号 需求 来源 优先级 验收标准
F1.1 多渠道会话接入 US-1 / R1 Must 支持接入淘宝、天猫、京东、拼多多、抖音 5 个平台；新消息到达至工作台可见延迟 ≤ 3 秒；客服可在单一界面查看并回复任意渠道消息，无需打开平台后台
F1.2 客户信息侧边栏 US-2 / R2 Must 打开会话即自动展示该客户的：近 90 天订单列表、当前物流状态、历史会话记录、历史工单；信息加载完成时间 ≤ 1.5 秒
F1.3 会话分配与转接 US-1 / R1 Must 支持按"平均分配 / 技能组 / 指定客服"三种策略分配；支持会话转接并附带转接原因备注；转接后接手方可看到完整上文
F1.4 一键升级主管 US-4 / R10 Should 客服可一键将会话升级至主管，升级时自动附带 AI 生成的会话摘要与已尝试的处理动作；主管端收到实时提醒
F1.5 快捷话术库 US-3 / R9 Should 支持按场景分类维护话术模板；客服可通过关键词检索并一键插入；支持话术使用次数统计

F2 AI 应答引擎

编号 需求 来源 优先级 验收标准
F2.1 售后意图识别 R3 Must 覆盖 Day 2 定义的 15 个售后场景；在测试集上意图识别准确率 ≥ 90%；单次识别响应 ≤ 800ms
F2.2 规则引擎应答 R3 Must 对"查物流、查退款进度、催发货"等规则明确场景走确定性规则路径，不经大模型生成；命中率 ≥ 95%，零幻觉
F2.3 大模型生成应答 R3 Must 复杂场景由大模型基于知识库生成回复；回复需标注引用来源；支持商家配置"禁用话题"（如价格谈判）
F2.4 知识库管理 R9 Must 支持 FAQ 批量导入（Excel/CSV）；支持按商品 SKU 绑定专属知识；支持设置知识生效时间（如大促临时政策）
F2.5 置信度与转人工策略 R3 Must 商家可配置置信度阈值（默认 0.85）；低于阈值或连续 2 轮未解决时自动转人工；转人工时携带 AI 已收集的信息与建议方案，避免客户重复描述
F2.6 情绪识别与安抚 US-4 / R10 Could 识别客户负面情绪并提示客服；高风险情绪（辱骂、投诉威胁）自动优先排队并提醒主管
F2.7 多轮上下文记忆 R3 Should 单会话内支持 ≥ 10 轮上下文；客户中途补充信息（如订单号）能被正确关联到原诉求

F3 AI 任务执行（核心差异化）

本模块是"能办事"与"只会答题"的分界线，也是相对于美洽等低价竞品的核心壁垒。

编号 需求 来源 优先级 验收标准
F3.1 订单查询 Agent R5 Must AI 可根据客户提供的手机号/订单号/商品名调用订单 API 查询；查不到时引导客户提供更多信息而非直接转人工
F3.2 物流查询 Agent R5 Must 调用物流 API 返回实时轨迹与预计到达时间；物流状态为"已签收"但客户称未收到时，自动转入异常工单
F3.3 退款发起 Agent（条件自动） R5 Must 满足"7 天无理由 + 商品金额 ≤ 阈值 + 无历史恶意记录"时自动审批并执行退款；不满足时生成工单转人工；所有自动退款记录可逐笔追溯
F3.4 退货单生成 Agent R5 Should 退货申请通过后自动生成退货地址与物流单号并推送客户；支持上门取件预约
F3.5 电子发票开具 Agent R9 Should 客户提交抬头与税号后自动开具并推送；支持补开、改抬头（限未超过平台规定时限）
F3.6 物流异常主动检测 R6 Should 对"物流停滞超 48 小时""包裹退回""配送异常"主动识别并生成预警工单，在客户来问之前先发现

F4 工单系统

编号 需求 来源 优先级 验收标准
F4.1 工单创建与流转 R4 / R7 Must 会话可一键转为工单并自动带入客户、订单、会话摘要；支持指派、转派、协作处理；工单与会话双向关联
F4.2 工单状态机 R4 Must 定义完整状态流转（待受理 → 处理中 → 待客户确认 → 已完成 / 已关闭 / 已升级）；状态变更留痕，含操作人与时间戳
F4.3 SLA 监控与提醒 US-8 / R6 Should 支持按工单类型配置 SLA 时长；临期 80% 时提醒处理人，超期时标红并通知主管
F4.4 工单升级机制 US-4 / R10 Should 支持手动升级与自动升级（超期未处理、客户二次催办、金额超阈值）；升级路径可配置（主管 → 老板）
F4.5 工单模板自定义 R7 Could 商家可自定义工单字段与流转规则，适配非标业务

F5 审批与权限

本模块是打消客服主管顾虑的关键。主管怕 AI 乱来，就用规则 + 留痕解决。

编号 需求 来源 优先级 验收标准
F5.1 角色权限矩阵 US-12 / R4 Must 预置三类角色（客服 / 主管 / 管理员），覆盖会话、工单、退款、配置、数据五类权限；支持自定义角色
F5.2 金额阈值自动审批 US-6 / R4 Must 商家可设置自动审批金额上限（默认 200 元）；阈值内自动执行，超阈值按层级审批；阈值可按商品类目分别配置
F5.3 操作日志与留痕 US-9 / R4 Must 所有退款、赔偿、权限变更操作记录操作人、时间、前值后值；日志保留 ≥ 180 天且不可删除
F5.4 审批流可视化配置 R4 Could 通过拖拽配置多级审批流，适配规模较大的团队

F6 数据看板

编号 需求 来源 优先级 验收标准
F6.1 实时运营看板 US-7 / R7 Should 展示当前排队会话数、平均响应时长、在线客服数、今日工单量；数据刷新间隔 ≤ 30 秒
F6.2 AI 效果报表 US-11 / R8 Should 展示 AI 拦截率、一次解决率、转人工率、平均处理时长（区分 AI 与人工）；支持按日/周/月与场景维度下钻
F6.3 团队效能报表 US-7 / R7 Should 展示每位客服的处理量、平均响应时长、一次解决率、SLA 达成率；支持导出
F6.4 成本节省核算 US-11 / R8 Should 按"AI 处理量 × 人工单条成本"估算节省金额，并折算为等效人力数；口径与计算过程对商家透明可查
F6.5 未解决会话聚类 US-10 / R11 Could 对转人工与未解决的会话自动聚类，输出高频缺口 TOP 10，指导知识库补充
F6.6 售后问题分布与趋势 US-14 / R12 Could 按问题类型、商品 SKU 维度统计分布与环比趋势，支持导出用于供应链复盘

四、关键优先级决策说明

挑几条有代表性的，说明为什么这么排。

F3.3 退款发起 Agent → Must

理由：这是"能办事"承诺的兑现点。没有它，产品就退化成又一个"只会答题的机器人"，与美洽无异。虽然涉及资金有风险，但通过"条件自动 + 金额阈值 + 全程留痕"三重约束，风险可控。且不做这条，AI 拦截率无法突破 60% 的目标，核心 ROI 不成立。

F5.2 金额阈值自动审批 → Must（而非 Should）

理由：它是 F3.3 的技术前提。没有阈值规则，每一笔退款都要人工点确认，AI 就只省了"填表"的时间，没省"决策"的时间。同时它直击主管"权限不清、客服擅自赔偿"的高严重度痛点。

F6.4 成本节省核算 → Should（而非 Must）

理由：老板最关心"这钱花得值不值"，看似应该是 Must。但它只影响续费决策，不影响产品能否跑通主流程。且它需要 F6.2 的 AI 效果数据作为基础，存在依赖。先让产品能用，再证明它有用。

F2.6 情绪识别 → Could（而非 Should）

理由：需求真实（客服怕被骂），但技术成熟度和准确率在售后场景下不稳定，误报会干扰正常工作流。放到 V2.0，等技术验证充分再做。

F3.6 物流异常主动检测 → Should

理由：体验亮点（客户还没问，我们已经发现），但对 V1.0 主流程非必需。且强依赖物流 API 的数据质量，存在外部不确定性。

五、版本范围

版本 范围 目标
V1.0 全部 Must（16 条）+ F1.4、F1.5、F2.7、F3.6、F4.3、F4.4、F6.2 跑通"AI 自动处理 + 人工兜底"主闭环，可交付首批种子客户
V1.5 剩余 Should（F3.4、F3.5、F6.1、F6.3、F6.4） 补齐数据闭环，支撑续费决策
V2.0 全部 Could（F2.6、F4.5、F5.4、F6.5、F6.6） 差异化深化与智能化

六、本期明确不做

敢说不做什么，和知道要做什么一样重要。

不做 原因
售前咨询与营销获客 定位是售后工作台，售前有专门工具（且是红海），不分散精力
呼叫中心 / 电话客服 中小电商售后以在线消息为主；电话涉及线路资源与硬件，成本结构完全不同
私有化部署 目标客户无强合规需求；SaaS 更轻、上线更快，符合"一周上线"目标
CRM / 会员管理 超出售后边界，且与商家现有系统重叠，容易变成又一个没人用的模块
多语言 / 跨境 目标客户以国内平台为主；跨境是另一个战场，需要完全不同的能力栈
自定义大模型接入 V1.0 由平台统一提供模型能力，避免商家陷入选型困境；待 V2.0 有明确需求再开放
