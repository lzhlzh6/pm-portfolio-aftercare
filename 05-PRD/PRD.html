一、背景与目标

1.1 问题陈述

中小电商商家（5-15 人客服团队）在售后环节面临三个结构性问题：

  1. 重复劳动占比高：约 70% 的售后咨询是重复问题（查物流、查退款进度、退换货政策），但全部由人工处理。
  2. 渠道割裂：客服需在淘宝、京东、拼多多、抖音等多个平台后台间切换，信息不同步，响应慢。
  3. 现有 AI 客服"只会答题，不会办事"：信通院数据显示 86% 的智能客服项目效果不及预期，具备完整 Agent 自主决策能力的产品不足 15%。典型表现是——客户问"我的货到哪了"，机器人回复一段物流查询教程，而不是直接调 API 查出结果。

1.2 产品定位

一句话：面向中小电商商家的 AI 售后工作台，让 AI 不只是回答问题，而是直接把事办完。

维度 定位
目标客户 5-15 人客服团队的中小电商商家
核心场景 售后（不含售前营销）
差异化 AI 任务执行能力（查订单、查物流、自动退款），而非仅话术生成
价格带 年费 5-15 万，填补"美洽（3-8 万，做不了复杂工单）"与"智齿（30-50 万，中小企业买不起）"之间的价格断层

1.3 目标用户

Persona 角色 核心诉求
王老板 商家老板 / 决策者 降低人力成本，钱花得值
李主管 客服主管 AI 可控、不出错、不惹客诉
小张 一线客服 少做重复劳动，别被 AI 替代

详见 Day 2 文档第二章完整 Persona。

1.4 成功指标

指标 目标值 说明
AI 拦截率 ≥ 60% AI 独立解决的会话数 / 总会话数
一次解决率 ≥ 75% 无需二次跟进即解决的会话数 / 总会话数
平均首次响应时长 ≤ 30 秒 从客户发起至首次收到回复
平均处理时长（AHT） 降低 ≥ 40% 对比上线前基线
客诉升级率 ≤ 5% 升级至主管或平台的会话占比

2.2 本期明确不做

不做 原因
售前咨询与营销获客 定位是售后工作台，售前是红海，不分散精力
呼叫中心 / 电话客服 中小电商售后以在线消息为主；电话涉及线路资源，成本结构不同
私有化部署 目标客户无强合规需求；SaaS 更轻，符合"一周上线"目标
CRM / 会员管理 超出售后边界，与商家现有系统重叠
多语言 / 跨境 目标客户以国内平台为主
自定义大模型接入 V1.0 由平台统一提供，避免商家陷入选型困境

三、术语表

术语 定义
会话（Session） 客户与客服（含 AI）之间的一次完整对话
工单（Ticket） 需要跨时段跟进或需多方协作的售后事项，由会话转化或系统自动生成
AI 拦截率 AI 独立解决、未转人工的会话数 / 总会话数
一次解决率 无需客户二次进线即解决的会话数 / 总会话数
置信度（Confidence） AI 对自身答复正确性的自评分数，0-1 之间，默认阈值 0.85
阈值（Threshold） 自动退款的金额上限，默认 200 元，可按商品类目覆盖
SLA 服务等级协议，指某类工单承诺的处理时长
AHT Average Handle Time，平均处理时长
转人工（Handoff） AI 将会话交给人工客服处理的动作
升级（Escalation） 工单从低权限处理人转移到高权限处理人的动作

四、角色与权限

4.1 角色定义

角色 说明 典型人数
系统（System） AI 与自动化规则，非自然人 —
人工客服（Agent） 一线处理会话与工单 5-15 人
客服主管（Supervisor） 管理团队，处理升级与审批 1-2 人
财务（Finance） 复核大额退款，管理账单 1 人
老板 / Owner 商家决策者，拥有全部权限 1 人

4.2 权限矩阵

完整矩阵见 Day 4 图 3。此处列出关键约束：

关键约束 说明
客服仅可查看自己的工单 数据隔离，避免串单与信息泄露
客服可发起 ≤ 阈值退款 阈值内无需审批，直接执行
客服不可发起 > 阈值退款 必须生成待审批工单
主管审批范围限本团队 跨团队大额退款需更高权限
财务仅可复核，不可发起退款 避免"既当运动员又当裁判员"
老板全权限但全部操作留痕 技术上能看到 ≠ 能做不被记录的事

4.3 权限变更规则

  • 角色由 Owner 或 Supervisor 分配，变更需二次确认。
  • 权限变更本身写入操作日志（见 F5.3），保留 ≥ 180 天。
  • 员工离职/转岗时，其进行中的会话与工单自动转派给直属主管，转派记录留痕。

五、功能需求详述

写作约定：每条需求按「功能描述 → 输入输出 → 业务规则 → 界面要素 → 异常流 → 验收标准」六段式展开。

5.1 F1 会话工作台

F1.1 多渠道会话接入（Must）

功能描述
将淘宝、天猫、京东、拼多多、抖音五个平台的客户消息汇聚到统一工作台，客服在单一界面完成查看与回复。

输入 / 输出

输入 输出
各平台推送的客户消息 工作台会话列表实时更新
客服输入的回复内容 回传至对应平台，客户可见

业务规则
1. 新消息到达至工作台可见延迟 ≤ 3 秒。
2. 同一客户在不同平台的会话，若手机号一致则自动合并为"同一客户视图"，但保留渠道标识。
3. 会话按"最后消息时间倒序 + 未读优先"排序。
4. 支持按渠道、处理状态、处理人筛选。

界面要素
- 左侧：会话列表（客户昵称、渠道图标、最后一条消息摘要、未读数、等待时长）
- 中间：对话区（消息气泡、输入框、快捷话术入口、转接/升级/建单按钮）
- 右侧：客户信息侧边栏（见 F1.2）

异常流

异常 处理
平台 API 断连 顶部红色横幅提示"XX 渠道连接中断，正在重连"；已收消息不受影响；重连后自动补拉中断期间消息
消息发送失败 输入框下方提示"发送失败，点击重试"；失败消息标红保留，不丢失
客户在 5 个平台同时进线 合并为一条会话，渠道标签显示多个图标；客服回复时可选渠道，默认全部回复

验收标准
- 支持接入 5 个平台，可正常收发消息。
- 新消息到达至工作台可见延迟 ≤ 3 秒（P95）。
- 客服可在单一界面完成 5 个平台的查看与回复，全程无需打开平台后台。

F1.2 客户信息侧边栏（Must）

功能描述
打开会话即自动展示该客户的相关业务信息，避免客服切后台查询。

展示内容

模块 字段
客户基本信息 昵称、手机号（脱敏：138****5678）、注册时间、累计订单数、累计消费金额
近 90 天订单 订单号、商品名、金额、下单时间、订单状态
当前物流 最近一笔订单的物流公司、运单号、最新轨迹节点、预计到达时间
历史会话 近 5 条会话的主题、处理人、处理结果
历史工单 近 5 条工单的编号、类型、状态、处理结果
风险标记 是否为高频退款客户（近 90 天退款率 > 30%）、是否在黑名单

业务规则
1. 信息加载完成时间 ≤ 1.5 秒。
2. 手机号默认脱敏，点击"查看完整号码"需二次确认并留痕。
3. 高频退款客户显示橙色警示标签，黑名单客户显示红色标签。

异常流
- 订单/物流 API 超时：对应模块显示"数据加载失败，点击重试"，其余模块正常展示，不阻塞会话处理。
- 客户无历史数据：显示空状态"暂无历史记录"。

验收标准
- 打开会话后 1.5 秒内（P95）完整展示上述 6 个模块。
- 手机号默认脱敏，查看完整号码需二次确认且写入操作日志。

F1.3 会话分配与转接（Must）

功能描述
新会话按策略自动分配给客服，并支持客服间转接。

分配策略

策略 规则 适用场景
平均分配 轮询分配给当前在线且负载最低的客服 团队技能均匀
技能组 按会话意图匹配对应技能组（如退款组、物流组） 团队有分工
指定客服 分配给特定客服 大客户专属服务

业务规则
1. 客服有并发上限（默认 8 个会话），达到上限后不再分配新会话。
2. 客服离线时，其进行中的会话自动转给在线同事，转接时携带完整上文。
3. 转接需填写转接原因（下拉选择 + 可选备注），接手方可见。
4. 转接后，客户侧不感知（不显示"已转接"提示），保持体验连续。

异常流
- 全员离线：会话进入"待分配队列"，显示排队位置；有客服上线后优先分配。
- 全员达并发上限：同上，但提示客户"当前咨询量较大，预计等待 X 分钟"。

验收标准
- 三种分配策略可配置且生效正确。
- 转接后接手方可看到完整上文与转接原因。
- 客户侧无"已转接"提示。

F1.4 一键升级主管（Should，本期纳入）

功能描述
客服遇到处理不了的会话，可一键升级至主管。

业务规则
1. 点击"升级"后，系统自动生成会话摘要（AI 生成，含客户诉求、已尝试动作、当前卡点）。
2. 主管端收到实时提醒（站内 + 可选短信）。
3. 升级后会话进入主管的待办列表，原客服仍可见但转为"协作"状态。
4. 主管处理后可选择"退回原客服"或"直接办结"。

验收标准
- 升级时自动附带 AI 生成的会话摘要。
- 主管端实时收到提醒（延迟 ≤ 5 秒）。

F1.5 快捷话术库（Should，本期纳入）

功能描述
按场景维护话术模板，客服可检索并一键插入。

业务规则
1. 话术按场景分类（退换货政策、物流解释、优惠券说明、安抚话术等）。
2. 支持关键词检索，支持按使用次数排序。
3. 支持插入变量（客户昵称、订单号、商品名），插入时自动替换。
4. 记录每条话术的使用次数，用于后续优化。

验收标准
- 支持按场景分类维护、关键词检索、一键插入。
- 变量自动替换正确。

5.2 F2 AI 应答引擎

F2.1 售后意图识别（Must）

功能描述
识别客户消息所属的售后场景，为后续分流提供依据。

意图列表（15 个，详见 Day 2 文档第三章）

编号 意图 典型表述
I1 查物流 "我的货到哪了"
I2 查退款进度 "退款什么时候到账"
I3 催发货 "怎么还没发货"
I4 申请退货 "我要退货"
I5 申请退款 "不想要了，退款"
I6 质量问题 "收到就是坏的"
I7 尺码/颜色不符 "发错颜色了"
I8 少件漏发 "少了一件"
I9 修改地址 "能改收货地址吗"
I10 开发票 "开个发票"
I11 优惠券/价保 "能补差价吗"
I12 使用咨询 "这个怎么用"
I13 投诉 "我要投诉"
I14 催人工 "转人工"
I15 其他 —

业务规则
1. 意图识别准确率 ≥ 90%（在标注测试集上）。
2. 单次识别响应 ≤ 800ms。
3. 识别为 I13（投诉）或 I14（催人工）时，直接转人工，不走 AI 应答。
4. 置信度低于阈值（默认 0.85）时，转人工。

验收标准
- 测试集上意图识别准确率 ≥ 90%。
- P95 响应 ≤ 800ms。

F2.2 规则引擎应答（Must）

功能描述
对规则明确的场景，走确定性规则路径，不经大模型生成，保证零幻觉。

适用意图
I1（查物流）、I2（查退款进度）、I3（催发货）——这三类占售后咨询约 45%。

业务规则
1. 命中规则后，调用对应 API 获取数据，用固定模板填充返回。
2. 不经大模型生成，杜绝幻觉。
3. 规则命中率 ≥ 95%。

示例

客户："我的货到哪了"
→ 识别为 I1
→ 提取订单号（或从客户信息侧边栏取最近订单）
→ 调用物流 API
→ 模板填充："您的订单已于 9 月 3 日从杭州发出，
   当前在【上海转运中心】，预计 9 月 6 日送达。"

验收标准
- 规则命中率 ≥ 95%，规则路径下零幻觉（人工抽检 100 条无事实性错误）。

F2.3 大模型生成应答（Must）

功能描述
复杂场景由大模型基于知识库生成回复。

业务规则
1. 仅对未命中规则的意图启用大模型。
2. 生成时必须携带知识库检索结果作为上下文。
3. 回复需标注引用来源（哪条知识/哪个文档），客服与客户均可查看。
4. 支持商家配置"禁用话题"（如价格谈判、承诺赔付），命中禁用话题时不生成，直接转人工。
5. 单次生成响应 ≤ 3 秒。

异常流
- 大模型超时（> 3 秒）：降级为"正在为您查询，请稍候"，并转人工。
- 检索不到相关知识：不强行生成，转人工并提示客服补充知识库。

验收标准
- 生成回复均标注引用来源。
- 禁用话题配置生效。
- P95 响应 ≤ 3 秒。

F2.4 知识库管理（Must）

功能描述
商家维护 FAQ 与商品知识，供 AI 检索使用。

功能点
1. 批量导入：支持 Excel / CSV 导入，模板含字段：问题、答案、适用 SKU、生效时间、失效时间。
2. SKU 绑定：知识可绑定特定商品 SKU，实现"问 A 商品时只检索 A 的知识"。
3. 生效时间：支持设置生效/失效时间，适用于大促临时政策。
4. 知识状态：草稿 / 已发布 / 已下线，仅"已发布"状态被检索。

业务规则
1. 导入时校验必填字段缺失与格式错误，错误行标红并给出行号。
2. 知识变更后，检索索引 5 分钟内生效。

验收标准
- 支持 Excel/CSV 批量导入，含错误行提示。
- 支持 SKU 绑定与生效时间设置。

F2.5 置信度与转人工策略（Must）

功能描述
定义 AI 何时放弃、交给人工。

转人工触发条件（满足任一即触发）

条件 说明
置信度 < 阈值 默认阈值 0.85，商家可调
连续 2 轮未解决 客户对 AI 回复表示否定或重复提问
客户明确要求人工 含"转人工""找客服"等表述
识别为投诉意图 I13
命中禁用话题 如价格谈判
大模型超时 > 3 秒未返回

业务规则
1. 转人工时，AI 需携带：已收集的信息（订单号、问题描述、客户诉求）、已尝试的动作、置信度、建议处理方案。
2. 客户无需重复描述问题。
3. 转人工后，会话进入待分配队列，按 F1.3 策略分配。

验收标准
- 六种触发条件均可配置且生效正确。
- 转人工时携带完整上下文，客服端可见。

F2.7 多轮上下文记忆（Should，本期纳入）

功能描述
单会话内保持上下文连贯。

业务规则
1. 支持 ≥ 10 轮上下文。
2. 客户中途补充的信息（如订单号）能正确关联到原诉求。
3. 会话结束后上下文清空，不跨会话记忆（避免隐私风险）。

验收标准
- 10 轮对话内，客户补充的信息能被正确关联。

5.3 F3 AI 任务执行（核心差异化）

本模块是"能办事"与"只会答题"的分界线，也是相对于美洽等低价竞品的核心壁垒。

F3.1 订单查询 Agent（Must）

功能描述
AI 根据客户提供的信息调用订单 API 查询。

业务规则
1. 支持的查询键：手机号、订单号、商品名。
2. 查到多条时，展示列表让客户选择（最多展示 5 条）。
3. 查不到时，引导客户提供更多信息（如"麻烦提供下单手机号后四位"），而非直接转人工。
4. 连续 2 次查询失败才转人工。

异常流
- 订单 API 不可用：回复"订单系统繁忙，正在为您转接人工"，同时转人工。

验收标准
- 支持三种查询键，查询成功率 ≥ 90%。
- 查不到时引导补充信息，连续 2 次失败才转人工。

F3.2 物流查询 Agent（Must）

功能描述
调用物流 API 返回实时轨迹。

业务规则
1. 返回：物流公司、运单号、最新 3 条轨迹节点、预计到达时间。
2. 特殊规则：物流状态为"已签收"但客户称未收到时，自动生成异常工单（类型：物流异常，优先级：高），转人工处理。

验收标准
- 实时轨迹返回正确。
- "已签收但客户称未收到"场景自动触发异常工单。

F3.3 退款发起 Agent（Must，本产品核心）

功能描述
满足条件时自动审批并执行退款，不满足时生成工单转人工。

完整决策树

退款请求进入
    │
    ├─ 步骤 1：判断退款理由
    │   ├─ 7 天无理由 → 进入步骤 2
    │   ├─ 质量问题 / 描述不符 / 少件 → 转人工（需人工看图判责）
    │   └─ 其他 / 无法判断 → 转人工
    │
    ├─ 步骤 2：判断金额
    │   ├─ 金额 ≤ 阈值（默认 200 元）→ 进入步骤 3
    │   └─ 金额 > 阈值 → 生成"待审批工单"→ 主管审批
    │       ├─ 通过 → 执行退款
    │       └─ 驳回 → 回到人工处理中（客户体感仍是同一客服）
    │
    ├─ 步骤 3：判断客户风险
    │   ├─ 近 90 天退款率 > 30% → 转人工
    │   ├─ 在黑名单 → 转人工
    │   └─ 正常 → 进入步骤 4
    │
    ├─ 步骤 4：判断商品风险
    │   ├─ SKU 在黑名单（高价值/易损）→ 转人工
    │   └─ 正常 → 进入步骤 5
    │
    └─ 步骤 5：✅ 自动执行退款
        ├─ 调用退款 API
        ├─ 推送通知客户（站内 + 短信）
        ├─ 生成工单（状态：已解决，标记"自动退款"）
        └─ 写入操作日志（含决策链路全记录）

关键业务规则

规则 定义
7 天无理由起算点 从签收时间起算，非下单时间。未签收订单不适用
阈值默认值 200 元。商家可按商品类目分别配置（如服饰 200 元、数码 500 元）
高频退款客户 近 90 天退款率 > 30%，转人工
黑名单 SKU 商家手动配置，典型为高价值商品、易损品、定制品
每日自动退款上限 单店每日自动退款总额上限（默认 5000 元），超出后转人工，防止异常批量退款

安全约束（三重）
1. 条件自动：必须全部满足决策树的 5 个步骤才自动执行。
2. 金额阈值：默认 200 元，可按类目覆盖。
3. 全程留痕：每一笔自动退款记录完整决策链路，可逐笔追溯。

异常流

异常 处理
退款 API 调用失败 重试 2 次；仍失败则生成"待处理工单"，标记"退款执行失败"，转人工
退款金额 > 订单实付 拦截，转人工（防止超额退款）
订单已退款过 提示"该订单已退款"，不重复执行
触发每日上限 转人工，并通知主管"今日自动退款额度已用尽"

验收标准
- 决策树 5 个步骤判断逻辑正确，边界值（恰好等于阈值）处理正确。
- 所有自动退款记录可逐笔追溯，含完整决策链路。
- 每日上限生效。

F3.6 物流异常主动检测（Should，本期纳入）

功能描述
在客户来问之前，主动发现物流异常。

检测规则

异常类型 触发条件 动作
物流停滞 轨迹超 48 小时无更新 生成预警工单
包裹退回 轨迹出现"退回"节点 生成预警工单，优先级高
配送异常 轨迹出现"配送失败""地址异常" 生成预警工单

业务规则
1. 扫描频率：每 2 小时全量扫描一次近 15 天的在途订单。
2. 生成预警工单后，系统主动联系客户（站内消息 + 短信模板），告知异常并提供解决方案选项。
3. 同一订单的同类异常只预警一次，不重复打扰。

验收标准
- 三类异常识别准确，无误报轰炸。
- 主动触达在客户进线前完成。

5.4 F4 工单系统

F4.1 工单创建与流转（Must）

功能描述
会话一键转工单，支持指派、转派、协作。

创建方式
1. 手动：客服在会话中点击"创建工单"，自动带入客户信息、订单信息、会话摘要。
2. 自动：退款超阈值、物流异常检测、AI 转人工时自动生成。

业务规则
1. 工单与会话双向关联：从工单可跳会话，从会话可看关联工单。
2. 支持指派（指定处理人）、转派（更换处理人）、协作（添加协作者）。
3. 工单字段详见第七章数据字典。

验收标准
- 一键转工单时自动带入客户、订单、会话摘要。
- 工单与会话双向跳转正常。

F4.2 工单状态机（Must）

状态定义（详见 Day 4 图 2）

状态 说明 可流转到
新建 工单刚创建 AI 处理中 / 待人工处理
AI 处理中 AI 正在尝试解决 已解决 / 待人工处理
待人工处理 等待人工接单 人工处理中
人工处理中 客服正在处理 待审批 / 已解决
待审批 退款 > 阈值，等待主管 已解决（通过）/ 人工处理中（驳回）
已解决 问题已答复，待关单 已关闭 / 待复审
待复审 客户对结果不满意 人工处理中
已关闭 终态 —

业务规则
1. 状态变更留痕，含操作人、时间戳、变更前后的值。
2. 已关闭为终态，不可再流转（如需重开，走"待复审"路径）。

验收标准
- 8 个状态流转正确，非法流转被拦截。
- 所有状态变更留痕可查。

F4.3 SLA 监控与提醒（Should，本期纳入）

功能描述
按工单类型配置处理时长，临期提醒，超期告警。

默认 SLA 配置

工单类型 首次响应 解决时长
退款类 30 分钟 4 小时
物流异常 1 小时 24 小时
质量问题 2 小时 48 小时
其他 4 小时 72 小时

提醒规则
1. 临期 80% 时，提醒处理人（站内 + 可选短信）。
2. 超期时，工单标红并通知主管。
3. 审批类工单 2 小时未审批，自动升级至上一级。

验收标准
- SLA 配置生效，提醒在正确时点触发。

F4.4 工单升级机制（Should，本期纳入）

升级触发条件

条件 说明
手动升级 客服点击"升级"按钮
超期未处理 超过 SLA 解决时长
客户二次催办 客户就同一问题二次进线
金额超阈值 退款金额 > 阈值

升级路径
可配置，默认：客服 → 主管 → 老板（两级封顶）。

业务规则

2. 升级次数记录在工单字段 escalation_count，用于后续分析。
3. 升级后原处理人转为协作者，可见但不负责。

六、核心业务流程规则汇总

6.1 意图识别与分流规则

客户消息进入
    │
    ├─ 意图识别（F2.1）
    │   ├─ 识别为 I13 投诉 / I14 催人工 → 直接转人工
    │   └─ 其他意图 → 继续
    │
    ├─ 规则引擎匹配（F2.2）

    │   └─ 未命中 → 继续
    │

    │   └─ 置信度 < 0.85 或命中禁用话题 → 转人工

    └─ 转人工（F2.5）→ 进入人工流程

6.2 退款决策规则（核心）

金额恰好 = 阈值 走自动退款（≤ 含等于）
签收刚好第 7 天 走 7 天无理由（含第 7 天）
近 90 天退款率恰好 30% 不算高频（> 30% 才算）

操作留痕 关键操作保留 ≥ 180 天，不可删除
权限隔离 客服仅可查看自己负责的数据
数据导出 导出行为留痕，导出文件加水印（含操作人与时间）

8.3 兼容性

  • 浏览器：Chrome / Edge 最新两个大版本。
  • 分辨率：≥ 1366 × 768。
  • 移动端：V1.0 提供主管端的响应式适配（仅查看与审批），客服端要求桌面。

8.4 可用性

项 要求
服务可用性 ≥ 99.5%
数据备份 每日全量 + 实时增量，保留 30 天
降级策略 大模型不可用时，降级为规则引擎 + 转人工，不影响基础客服功能

8.5 可扩展性

  • 渠道接入层需抽象为插件式，新增平台时核心逻辑不改。
  • 任务 Agent 需支持注册表式扩展，新增 Agent 不改主流程。

依赖方 用途 关键接口 风险

京东开放平台 同上 同上 同上

降级预案
- 大模型不可用 → 降级为规则引擎 + 全部转人工，基础客服功能不受影响。
- 某平台 API 不可用 → 该渠道消息暂不可用，其余渠道正常，顶部提示。
- 物流 API 不可用 → 物流查询转人工，其余功能正常。

10.2 核心指标计算口径

指标 计算式 数据来源
AI 拦截率 count(is_ai_resolved = true) / count(*) session
一次解决率 count(无需二次进线) / count(*) session
转人工率 count(handoff_reason 非空) / count(*) session
AHT（AI） avg(resolved_at - created_at) where assignee = system session
AHT（人工） avg(resolved_at - created_at) where assignee != system session
SLA 达成率 count(未超期) / count(*) ticket

口径说明：AI 拦截率的分子不含客户主动要求人工的会话（handoff_reason = customer_request），否则会低估 AI 能力。此口径需在看板上明示。

十一、异常与边界清单

# 场景 系统行为 客户感知
1 平台 API 断连 顶部红色提示，已收消息正常，重连后补拉 无感知（除延迟）
2 消息发送失败 标红保留，提供重试 提示"发送失败"
3 大模型超时 降级提示 + 转人工 "正在为您转接人工"
4 订单/物流 API 不可用 该模块显示重试，其余正常 轻微延迟
5 退款 API 调用失败 重试 2 次，失败生成待处理工单 "退款处理中，稍后通知"
6 退款金额 > 实付 拦截，转人工 无感知（转人工处理）
7 重复退款 提示已退款，不重复执行 "该订单已退款"
8 触发每日退款上限 转人工 + 通知主管 无感知（转人工处理）
9 全员离线 会话进排队队列，显示排队位 "预计等待 X 分钟"
10 全员达并发上限 同上 同上
11 客户在 5 平台同时进线 合并会话，回复可选渠道 无感知
12 员工离职/转岗 进行中会话与工单自动转派主管 无感知（同一客服继续）
13 知识库检索无结果 不强行生成，转人工 + 提示补知识 无感知（转人工处理）
14 物流异常重复检测 同订单同类异常只预警一次 不重复打扰
