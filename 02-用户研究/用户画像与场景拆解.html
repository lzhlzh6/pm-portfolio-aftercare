方法说明：本文的 Persona 基于公开行业资料、竞品产品文档与电商售后从业者访谈内容归纳而成。目标用户的行为特征与痛点推导有据可依，但具体数字（如会话量、团队规模）为合理区间假设，正式对外前应通过真实用户访谈校验。

一、角色定义

B 端产品的一个基本事实：用的人和买的人不是同一个。售后管家涉及四类角色，四者的诉求经常冲突。

角色 定位 关注什么 不关心什么
商家老板 / 运营负责人 决策者、付费方 ROI、上线速度、店铺评分、成本 界面细节、具体功能操作
客服主管 管理者、推动者 团队效率、权限管控、质检、报表 技术实现方式
一线客服 高频使用者 界面简单、信息集中、少重复劳动 成本、公司战略
消费者 服务的最终对象 问题快点解决、别踢皮球 谁在处理、用的什么系统

关键冲突点：老板想最大化 AI 替代率以省钱，客服主管担心 AI 出错引发客诉，一线客服担心 AI 抢饭碗。产品设计必须同时满足三方，否则推不动。

解法：不把 AI 定位成"替代客服"，而是定位成"替客服干掉重复劳动"。这既是产品叙事，也是推行策略——对老板讲人力成本，对主管讲可控性，对客服讲减负。

二、用户画像（Persona）

Persona 1：王磊 — 决策者

项 内容
年龄 / 身份 34 岁，某家居类目电商公司老板
经营规模 天猫 + 拼多多 + 抖音共 3 个店铺，月 GMV 约 200 万
团队 客服 8 人（含 1 名主管），两班倒
预算 年 3-5 万，要求 3 个月内见到效果

典型一天：上午看昨日数据，中午被主管告知大促排班缺口，下午处理一个升级到平台的投诉。

痛点
1. 大促期间售后量翻倍，临时招人来不及，招来了也来不及培训
2. 客服流失率高，新人上手要 2 周，培训成本反复支出
3. 售后处理慢导致差评和店铺评分下滑，直接影响平台流量分配——这是最痛的
4. 花了钱上系统，但说不清到底省了多少钱

目标：用现有 8 个人扛住明年翻倍的订单量，且不出重大客诉。

决策关注点：投入产出比、上线周期、数据安全（不愿把客户数据交给不靠谱的小厂）。

Persona 2：陈静 — 管理者

项 内容
年龄 / 身份 28 岁，客服主管，从业 5 年
管理规模 8 人团队，日均售后会话约 800 条
熟练度 熟悉各平台规则，能处理大部分疑难件

典型一天：处理 20+ 个升级工单，排下周班表，抽查 30 条会话记录。

痛点
1. 被重复性问题打断，真正需要判断的疑难件反而没时间细看
2. 排班难——大促和夜班没人愿意上
3. 质检靠抽检，覆盖率低，问题发现滞后
4. 权限不清：客服为了快点结案擅自承诺赔偿，最后公司买单
5. 无法实时知道哪个工单要超时，往往是客户催了才发现

目标：把 80% 的重复问题挡在下面，自己只处理真正需要判断的 20%。

关注点：能否设置自动规则、能否留痕追溯、报表是否可信。

Persona 3：小雨 — 执行者

项 内容
年龄 / 身份 22 岁，一线客服，入职 3 个月
工作状态 同时看管淘宝、京东、拼多多、抖音 4 个后台窗口
熟练度 熟悉基本操作，遇复杂情况需请教主管

典型一天：处理 150+ 条消息，其中约 70% 是重复问题。

痛点
1. 在 4 个平台后台之间反复切换，手忙脚乱且容易发错窗口（最痛）
2. 重复问题回答到麻木："什么时候发货""怎么退货""能便宜点吗"
3. 查订单要跳出会话去 ERP 后台，来回切屏，客户等着急
4. 遇到情绪激动的客户不知道怎么接，怕被投诉
5. 新人记不住全部规则，遇到没见过的场景只能问主管

目标：少挨骂、少做重复劳动、遇到搞不定的能快速求助。

关注点：界面是否简单、信息是否集中、有没有话术推荐。

三、售后场景全景拆解

3.1 场景清单

按"AI 能接管到什么程度"给每个场景定级，这是决定产品边界的核心依据。

AI 可处理度定义

等级 含义 判定标准
全自动 AI 独立闭环，无需人工介入 规则明确、可调用 API 完成、无金额风险
条件自动 满足预设规则时自动执行，否则转人工 有明确判定条件，但存在例外情况
AI 辅助 AI 收集信息并生成方案，人工确认执行 需要看图、需要主观判断、涉及金额
人工为主 AI 仅做信息整理，决策与执行全人工 高风险、强沟通、需承担责任

场景全量表

# 场景 频率 复杂度 AI 可处理度 依赖系统
1 查物流（到哪了 / 何时到） 极高 低 全自动 物流 API
2 退款进度查询 高 低 全自动 支付 API
3 催发货（超时未发） 高 低 全自动 订单 API
4 7 天无理由退货 高 中 条件自动 订单 + 物流 + 支付
5 仅退款（未发货） 中 低 条件自动 订单 + 支付
6 开 / 补电子发票 中 低 全自动 发票系统
7 修改收货地址 中 低 条件自动 物流 API（未发货才可改）
8 物流异常（停滞 / 退回 / 错发） 中高 中 AI 辅助 物流 API
9 退货退款（质量问题） 中高 中 AI 辅助 订单 + 物流 + 支付
10 描述不符 / 色差 / 尺寸偏差 中 中 AI 辅助 订单
11 缺件少件（赠品 / 配件缺失） 中 中 AI 辅助 订单
12 补偿协商（优惠券 / 部分退款） 中 高 AI 辅助 优惠券 + 支付
13 差评协商修改 中 高 人工为主 评价 API
14 平台投诉 / 介入 低 高 人工为主 平台后台
15 大额争议申诉 低 高 人工为主 全系统

3.2 场景分布矩阵

（见配套图：以"发生频率"为横轴、"AI 可自动化程度"为纵轴的四象限矩阵）

象限 场景 产品策略
右上：高频 + 高自动化 查物流、查退款进度、催发货、7 天无理由退货 V1.0 核心，AI 全自动吃下。这批场景占比最大且规则明确，是 ROI 最高的部分
右下：高频 + 低自动化 退货退款执行、质量问题判定、物流异常 V1.0 重点，做人机协同。AI 负责信息归集与方案生成，人工做最后判断
左上：低频 + 高自动化 开电子发票、修改地址 V1.5 顺手做。实现成本低，作为功能完整度补充
左下：低频 + 低自动化 补偿协商、差评处理、平台投诉、大额争议 暂不投入。低频高风险，自动化收益低且出错代价大

3.3 AI 能力边界的判断依据

这是本项目最能体现技术理解的部分。判断一个场景能否自动化，看四个条件：

条件 说明 举例
信息可得 判断所需的数据能否通过 API 拿到 查物流需要物流 API，拿不到就无法自动
规则明确 判定条件能否写成确定逻辑 "7 天无理由"有明确时限，可写规则
动作可执行 结果能否通过 API 直接完成 退款需要支付 API 的退款接口权限
风险可控 出错的代价是否在可承受范围 小额退款可自动，大额必须人工

四个条件同时满足 → 全自动；缺"规则明确"或"风险可控" → 转 AI 辅助。

举例说明为什么"质量问题退货"只能做到 AI 辅助：
- 信息可得 ✓（订单 API 能拿到商品、购买时间）
- 规则明确 ✗（"是不是质量问题"需要看图，模型判断有误差）
- 动作可执行 ✓（支付 API 可退款）
- 风险可控 ✗（误判导致商家损失货款）

→ 结论：AI 负责收集订单信息、引导用户上传图片、按历史相似案例给出建议方案，由人工确认责任归属后执行。

四、用户故事

4.1 一线客服

  1. 作为同时看管 4 个平台的客服，我希望所有店铺的售后消息汇总到一个工作台，以便不用在多个后台之间来回切换。
  2. 作为一线客服，我希望在处理会话时就能看到该客户的订单、物流和历史会话，以便不用跳到后台查完再回来。
  3. 作为入职 3 个月的新人客服，我希望系统根据客户的问题自动推荐处理方案和话术，以便不用背完所有规则才能上岗。
  4. 作为一线客服，我希望遇到情绪激动的客户时能一键升级给主管，以便不用独自承担压力。
  5. 作为一线客服，我希望重复性问题（查物流、催发货）由系统自动回复，以便我能专注处理需要判断的复杂问题。

4.2 客服主管

  1. 作为客服主管，我希望按金额和场景设置自动审批规则，以便小额退款不用我逐个点确认。
  2. 作为客服主管，我希望看到每位客服的响应时长、一次解决率和质检分数，以便做绩效评估和培训安排。
  3. 作为客服主管，我希望超过 SLA 未处理的工单自动标红并提醒，以便不会漏掉快要爆的雷。
  4. 作为客服主管，我希望所有退款和赔偿操作留痕可追溯，以便出现纠纷时能查到是谁批的。
  5. 作为客服主管，我希望看到 AI 处理不了的会话都卡在哪，以便知道该补充哪些知识库内容。

4.3 商家老板

  1. 作为商家老板，我希望看到 AI 处理了多少售后、相当于省了几个人的工作量，以便判断这笔钱花得值不值。
  2. 作为商家老板，我希望客服的操作权限可控，以便不会出现客服擅自大额赔偿的情况。
  3. 作为商家老板，我希望新系统在一周内上线，以便不用等几个月的实施周期。
  4. 作为商家老板，我希望看到售后问题的类型分布和趋势，以便反过来优化商品质量和供应链。
